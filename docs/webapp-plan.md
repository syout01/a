# Web アプリ化とログイン設計

> 2026-09 更新：段階 1 は実装済み。決定事項＝クライアント向け閲覧アカウントは作らない（スプレッドシート共有で対応）、メール後架電の運用はしない。
> 配置手順は [deploy-render.md](deploy-render.md)。

## 実装済み（段階 1）

- メール＋パスワードのログイン、初回セットアップ画面、招待リンク／再設定リンク（管理者が発行して手渡し。メール送信サービス不要）
- 権限：管理者／担当者。管理操作はサーバー側で検証。担当者には管理者タブを表示しない
- セッション：ハッシュ保存、HttpOnly / SameSite=Lax / Secure、14 日、停止・再設定で即失効
- CSRF（カスタムヘッダ＋Origin 検証）、ログイン試行制限、セキュリティヘッダ（CSP など）、監査ログ
- 日次バックアップ（14 世代）と画面からのダウンロード
- Dockerfile、render.yaml

## 見送り

- クライアント企業ごとのテナント分離・閲覧専用ロール（段階 2）。クライアントへはスプレッドシート共有で対応する。
- Google ログイン。必要になったらメールアドレスをキーにそのまま足せる。

## 1. 段階

| 段階 | 状態 | 主な作業 | 目安 |
| --- | --- | --- | --- |
| 0（今） | ローカル起動。ログインなし。「自分」を手で選ぶ | ― | ― |
| 1 | クラウドに 1 インスタンス。全員がメール＋パスワードでログイン。担当＝ログインユーザー | 認証、セッション、招待、HTTPS、バックアップ | 2〜3 日 |
| 2 | クライアント企業ごとにデータを分離。権限（管理者／担当者／閲覧） | テナント（組織・クライアント）モデル、全クエリのスコープ、閲覧専用画面 | 1 週間 |

段階 1 を先にやるのは、認証を入れる時点でテーブル設計（誰が何を見られるか）を決める必要があり、段階 2 の下地がそこで固まるためです。

## 2. ログイン・ID 設計

### ID
- **ログイン ID はメールアドレス**。社内で一意で、招待・パスワード再設定に使える。
- 表示名（担当者名）は別に持つ。既存の「担当者」マスタは、ユーザーに統合する（`members` → `users`）。
- 段階 3 で Google ログインを足すときも、メールアドレスがキーになるので移行が要らない。

### パスワード・セッション
- パスワードは argon2id でハッシュ化（`argon2` パッケージ）。最低 10 文字。
- セッションは Cookie（HttpOnly、Secure、SameSite=Lax）。サーバー側の `sessions` テーブルに保存し、失効・強制ログアウトができるようにする。
- ログイン試行はメール単位で 10 回／15 分に制限。
- パスワード再設定は、メールで 30 分有効のリンクを送る（Resend など送信 API を 1 つ契約）。

### 招待制
- 自己登録はさせない。管理者が「招待」でメールを入力 → 招待リンクが送られる → 開いた人が名前とパスワードを設定して有効化。
- 招待リンクは 7 日で失効。

### ロール

| ロール | できること |
| --- | --- |
| オーナー | 組織の設定、課金、メンバー管理、すべて |
| 管理者 | 展示会作成・取り込み・ルール・割当・書き出し・メンバー招待 |
| 担当者 | 自分の担当リードのフォロー、担当外は閲覧のみ |
| 閲覧 | ダッシュボードと一覧の閲覧のみ（クライアントに発行する想定） |

## 3. テナント設計（段階 2）

テレアポ代行として複数のクライアント企業のフォローを回すので、階層は次の 3 段にします。

```
organization（運用会社。例：自社）
 └─ client（クライアント企業。ランク定義・ルール・担当者の範囲はここに紐づく）
     └─ exhibition（展示会）
         └─ leads / activities
```

- ユーザーは organization に属し、client 単位で「担当できる／見られる」を付与する。
- **セグメントとルールは client 単位** に持たせる。マニュアル 6.4 の「商材ごとの適合条件」がここに対応する。
- すべてのテーブルに `organization_id` を持たせ、API はログインユーザーの組織以外を一切返さない（ミドルウェアで強制）。
- クライアントに閲覧アカウントを出す場合、その client だけが見える organization 外ユーザーとして扱う。

## 4. ホスティング

| 候補 | 向き | 備考 |
| --- | --- | --- |
| Render（Web Service + Persistent Disk） | 段階 1 | 設定が最も少ない。SQLite をそのまま使える。月 1,000〜3,000 円程度 |
| Fly.io（Volume 付き） | 段階 1〜2 | 東京リージョンあり。Litestream で S3 へ継続バックアップしやすい |
| さくら VPS / AWS Lightsail + Docker | 自社で握りたい場合 | 手間は増えるが月額固定 |
| Postgres（Supabase / Neon）へ移行 | 段階 2 以降で件数が数十万を超えたら | それまでは SQLite で十分 |

推奨：**段階 1 は Render または Fly.io**。SQLite のままで、バックアップは Litestream（または 1 日 1 回 `app.db` をオブジェクトストレージへコピー）。

必要なもの：独自ドメイン（例 `leads.example.co.jp`）、HTTPS（ホスティング側が自動発行）、メール送信 API。

## 5. コードの変更点（段階 1）

1. `users`（id, email, name, password_hash, role, active）、`sessions`、`invitations`、`password_resets` テーブルを追加。既存 `members` は `users` に移行し、`leads.assignee_id` と `activities.member_id` はそのまま `users.id` を指す。
2. ログイン画面（`/login`）、招待受諾画面、パスワード再設定画面を追加。
3. すべての `/api/*` に認証ミドルウェア。未ログインは 401。
4. 画面右上の「自分」セレクタを廃止し、ログインユーザーを表示。フォロー画面の既定フィルタはログインユーザー。
5. 「記録して次へ」の記録者はサーバー側でログインユーザーに固定（クライアントからの `member_id` を信用しない）。
6. 設定タブに「メンバー招待」「ロール変更」「停止」。
7. `Dockerfile` と `render.yaml`（または `fly.toml`）、環境変数（`SESSION_SECRET`、`MAIL_API_KEY`、`APP_URL`）。
8. レート制限（`express-rate-limit`）、セキュリティヘッダ（`helmet`）、CSRF は SameSite Cookie とカスタムヘッダで対処。

## 6. 運用で決めておくこと

- **個人情報の保持期間**：展示会から何か月で削除するか（例：12 か月）。削除はツールに「展示会を削除」があるので、運用ルールだけ決める。
- **クライアントとの取り決め**：リストの二次利用禁止、閲覧アカウントの範囲。
- **バックアップの確認**：月 1 回、バックアップから復元できるかを試す。
- **退職者対応**：ユーザーを「停止」にすればログイン不可。担当リードは③で配り直す。

## 7. 判断が必要な点

1. クライアントに閲覧アカウントを出すか（出すなら段階 2 を早める）。
2. Google Workspace を使っているなら、最初から Google ログインだけにする選択もある（パスワード再設定の仕組みが不要になる）。
3. ホスティングを自社アカウントで契約するか。
